## 通知配置（两套，别混）
- **Plasma 会话**：plasmanotifyrc → `[Notifications] PopupTimeout = 15000`（毫秒，15 秒）。
- **niri / dwm 会话**：用 dunst，配置在 stow 包 `dunst`（`~/stow_config/dunst/.config/dunst/dunstrc`）。
  - 关键设置：`notification_limit = 5`、`pause_on_mouse_over = false`、
    urgency timeout 分别 5 / 15 / 30 秒，
    以及规则 `[force-timeout-on-never-expire]`（`match_dbus_timeout = 0` + `override_dbus_timeout = 15`），
    专门按死浏览器/Electron 传 `timeout=0` 导致永不消失的通知。
  - 配色对齐 ghostty 的 Tomorrow Night Eighties（bg `#282c34`）。
  - **注意**：`override_dbus_timeout` 是**规则级**属性，不能写进 `[global]`（已查 dunst 源码 settings_data.h 确认）。
  - Plasma 会话下**不要**启动 dunst，否则会和 plasmashell 抢 org.freedesktop.Notifications。
  - dunst 在 Arch 上：`sudo pacman -S dunst`；改配置后 `dunstctl reload`。

### 卡死通知的应急清理（Plasma 会话，不注销）
按侵入性递增，先轻后重：
1. 点托盘铃铛 → 通知历史 → 单条 X 或「清除全部」（KDE 官方论坛对「X 点了没反应」的首选）
2. `qdbus6 org.freedesktop.Notifications /org/freedesktop/Notifications org.freedesktop.Notifications.CloseNotification <id>`
   （活动通知的 id 用 `...GetNotifications` 列出来；屏幕上的弹窗属于 **活动** 通知）
3. 重启 plasmashell —— **先看 SubState，别盲目重试**：`systemctl --user status plasma-plasmashell.service`
   - `running`：`systemctl --user restart plasma-plasmashell.service`（Wayland 会话下 plasmashell 由 systemd 拉起），
     退回方案 `kquitapp6 plasmashell; sleep 1; setsid plasmashell >/dev/null 2>&1 &`
   - `deactivating (stop-sigterm)` / `failed` / `Result: timeout`：**systemd 卡在停止流程，此时 restart / stop 全是排队空转、永不执行**，必须
     `systemctl --user kill -s KILL plasma-plasmashell.service` → `sleep 1` →
     `systemctl --user reset-failed plasma-plasmashell.service`（**这步不能省，否则下次 start 还是被挡住**）→
     `systemctl --user start plasma-plasmashell.service`
   - 纠正：`list-unit-files` 里的 `disabled` 只表示不开机自启，**不代表 systemd 没在管它**，别据此下判断。
4. 最后手段 `pkill -9 plasmashell`（Wayland 下【不会】关闭应用窗口）；仍无效则 `journalctl --user -b -p err`

要点：
- Plasma 6.7+ 有可绑定的全局快捷键「清除通知历史记录」（`~/.config/kglobalshortcutsrc` 的 `[plasmashell]` 段，键名 `clear history`），
  但**它清的是历史记录，对还挂在屏幕上的活动弹窗不一定有效**。
- **Plasma 6 没有清空通知历史的 D-Bus 方法**（`org.kde.NotificationManager` 只暴露 InvokeAction / RegisterWatcher / UnRegisterWatcher），
  所以「定时自动清空通知中心」在 Plasma 上**做不到**，别再承诺这个。
- 本机 Plasma 版本 ≥ 6.7（探针：`/usr/share/xdg-desktop-portal/portals/plasmanotify.portal` 存在）。
- **「重启了也没用」的典型原因**：plasmashell 假死（或被 GPU 上下文丢失冻住，KDE bug 525886，
  journal 特征串 `QRhiGles2: Context is lost`）后，屏幕永久停在最后那一帧 —— 通知就表现为「点不动也不消失」。
  判断依据是 `systemctl --user status` 的 SubState，不是反复重试命令。
- 若重启 plasmashell 后残影仍在 => 它**不是 plasmashell 画的**，用 KWin 的 D-Bus 手段定位：
  `qdbus6 org.kde.KWin /KWin org.kde.KWin.queryWindowInfo`（鼠标变准星，点那块东西拿到窗口信息）
  / `org.kde.KWin.killWindow`（点哪关哪） / `org.kde.KWin.showDebugConsole`（窗口清单，含 PID）。
  再不行 `cascadeDesktop` + `unclutterDesktop` 强制整屏重绘冲残帧；**都不行就只能重启会话**
  （Wayland 下 `kwin_wayland --replace` 会带走所有窗口 ≈ 注销，别试）。
  注意 `/KWin` 上**没有** `toggleCompositing`（网上流传的命令是错的）。

## DNS / 网络（本机实测结论）
- **本机没有系统级 DNS 缓存**：`systemd-resolved` disabled、`nscd` 未装、`dnsmasq` 未跑、无 unbound/named，
  glibc 自身不缓存 → 所谓"清 DNS 缓存"在本机基本无事可做。
- **`/etc/resolv.conf` 由 dhcpcd 生成**（文件头自述 `Generated by dhcpcd from wlan0.dhcp...`），
  当前内容 = 路由器 `10.168.1.1` + IPv6 link-local `fe80::e240:7ff:feb3:31a4%wlan0`。
  **直接编辑该文件无效**，联网/续约时会被重写。
- 要换 DNS，走 dhcpcd hook 的插入点（`/usr/lib/dhcpcd/dhcpcd-hooks/20-resolv.conf` 第 61-78 行已确认顺序）：
  `header → /etc/resolv.conf.head → DHCP 下发的 servers → /etc/resolv.conf.tail`。
  即 **`.head` 优先于路由器，`.tail` 排在最后**；两文件当前都不存在。
  - `resolv.conf(5)` 手册原文：**"Up to MAXNS (currently 3) name servers may be listed"** —— 只有前 3 条生效；
    且算法是「某个服务器**超时**才换下一个」，所以第一个服务器若明确回 NXDOMAIN 就是终局
    → `.head` 放 2 条、第 3 个名额留给路由器兜底最合适；但只有路由器能解析的内网域名会因此失败。
  - 另一条路：`/etc/dhcpcd.conf` 加 `static domain_name_servers=...`（全局，全接口生效，替换掉 DHCP 的）；
    `nohook resolv.conf` = 让 dhcpcd 完全别碰该文件。
- **NetworkManager 虽 enabled 但空转**：`/etc/NetworkManager/system-connections/` 不存在、无运行时连接 →
  **wlan0 由 dhcpcd 管**。另外 `iwd.service` 也是 enabled。dhcpcd + NM 双开是历史遗留隐患（两者都想写 resolv.conf）。
- `/etc/hosts` 里有 10 条手写映射（2 条 demo 域名→127.0.0.1，8 条 `*.jtw.beijing.gov.cn`→固定 IP），
  **优先级高于 DNS 和一切缓存**，调这些域名时改 DNS/清缓存都没用。
- 选公共 DNS 的注意事项：`114.114.114.114` 可用但会劫持 NXDOMAIN（返回广告页，调试域名存在性时会误导）；
  `8.8.8.8` 在中国大陆常被污染/丢包，不宜做主力。推荐 `223.5.5.5` / `119.29.29.29`。
- 沙箱内 `sudo` 不可用，改 `/etc` 下的东西只能给茶命令让他自己跑。

## 已装通知守护（本机实测，2026-10-15 复查）
- KDE 原生：`plasma-workspace 6.7.5`，plasmashell 提供 `org.kde.plasma.Notifications`，**本应持有总线**（XDG_CURRENT_DESKTOP=KDE, wayland）。
  - ⚠️ 2026-10-15 实测：茶在 KDE 下打开系统设置→通知，显示"由 emersion mako 提供"——即 mako 被**手动启动**并抢走了 `org.freedesktop.Notifications`，Plasma 通知中心被架空。mako 无任何自启文件（无 service / 无 autostart / 无 DBus 激活），是手动起的；杀掉 mako + 重启 plasmashell 即可夺回总线。
- 另装了三个独立守护（都支持 Wayland，已确认链接 libwayland）：
  - `dunst 1.13.2`：已配好 stow 的 `dunstrc`；DBus 自动激活文件 `org.knopwob.dunst.service` 存在；**无 [Install]，不会自启**，需会话手动 spawn；**X11/Wayland 通吃**（dwm 唯一可用）。
  - `mako 1.11.0`：`~/.config/mako` 无配置；**无 systemd 服务文件，只能手动起（不会自启）**；**仅 Wayland**。
  - `swaync 0.12.6`：`~/.config/swaync` 有 2024 年的 config.json+css；**无 systemd 服务文件，只能手动起**；自带通知中心 GUI；**仅 Wayland**。注意其 config.json 里 `"timeout-critical": 0`（紧急通知永不自动关，是堆积隐患）。
  - `libnotify 0.8.8` 是**客户端**（notify-send），不是守护。
- 未装：fnott / xfce4-notifyd / notify-osd / notification-daemon / herbe / twmn。
- **关键规则（总线独占）**：`org.freedesktop.Notifications` 同一时刻只能一个守护持有。
  - KDE 会话下 plasmashell 已持有 → **勿**再起 dunst/mako/swaync。
  - niri/dwm 下三选一，三者都只能手动起（无自启服务文件），**别同时手动起两个**抢总线；且 KDE 会话下绝不起它们。
  - 实测三者都未自启 → niri/dwm 会话下通知目前是**真空（无人接管）**，不是卡死。

## 通知守护统一决策（2026-10-15，茶拍板方案 1）
- **KDE 保留 Plasma 原生**（已设 15s；不卸载、不抢总线）。
- **niri / dwm 统一用 dunst**，卸载 mako、swaync（这俩在 niri/dwm 下被 dunst 取代，且 mako/swaync 不支持 X11 的 dwm）。
- 启动方式：
  - niri：`~/.config/niri/config.kdl` 加 `spawn-at-startup "dunst"`（只在 niri 会话生效，不会进 KDE，所以不会抢总线）。
  - dwm：`~/.xinitrc` 加 `[ "$XDG_CURRENT_DESKTOP" != "KDE" ] && dunst &`。
- 脚本 `notif-unify.sh`（本工作区目录，未提交）：默认预演，`sudo bash notif-unify.sh --apply` 才执行
  （卸载 mako/swaync + 补启动项 + 校验）。沙箱内 pacman 读不到 → 预演会误报"未安装"，真实终端正常。
- **隐患**：`~/.config/niri` 目录**属主是 root**、且**未纳入 stow** → 改了本机也同步不到 ThinkBook；
  建议把 niri 配置也 stow 化，并在 ThinkBook 单独跑脚本或手动加启动行。
- 为何 KDE 不换 dunst：双守护同活会让应用发通知卡 60s；且会丢 KDE 通知中心（铃铛/历史/操作按钮/勿扰/锁屏）。
